# Server

Self-hosted Minecraft on an AWS EC2 host: a single Docker container
running a Fabric server, built from a Modrinth modpack defined in this
repo.

## Layout

```
Server/
├── docker-compose.yml    # the entire stack -- one service
├── .env.example          # copy to .env; all values optional
├── aws/
│   └── NOTES.md          # instance spec, security group, DNS
└── minecraft/
    ├── pack.yaml         # source of truth: mods, datapacks, versions
    ├── build.py          # compiles pack.yaml -> dist/pack.mrpack
    ├── MODLIST.md        # generated by build.py -- do not hand-edit
    ├── overrides/        # config files baked into the pack
    └── dist/             # build output (gitignored)
```

## Deploy

From a clean host with Docker installed:

```bash
git clone <this-repo> && cd Server
cp .env.example .env          # edit if you want; defaults work
cd minecraft && ./build.py && cd ..
docker compose up -d
```

`build.py` is a [uv](https://docs.astral.sh/uv/) script -- uv installs
its one dependency (PyYAML) automatically, no venv or pip install
needed. It also needs network access to Modrinth. Everything else the
server needs is fetched by the container at startup from the pack it
just built.

## Architecture

One container, `itzg/minecraft-server`. At startup it reads
`minecraft/dist/pack.mrpack`, installs the Fabric loader plus every mod
and datapack the pack marks as server-side, and runs the server. World
data lives in `./data`, bind-mounted so it survives container
replacement.

There is deliberately no control panel, no database, and no separate
daemon. The previous iteration ran Pterodactyl (Panel + Wings + MariaDB +
Redis); it was retired because a four-service control plane for a
single small server produced more failure modes than it prevented --
most of them in the networking between its own containers.

No IaC layer -- infrastructure is provisioned manually per
`aws/NOTES.md`.

## Requirements

- Docker Engine + the Compose plugin
- [uv](https://docs.astral.sh/uv/), to build the pack
- An AWS EC2 instance (spec in `aws/NOTES.md`)
- A DNS provider supporting A and SRV records

## Operating

| Task | Command |
|---|---|
| Status | `docker compose ps` (healthcheck reports real server readiness) |
| Logs | `docker compose logs -f minecraft` |
| Console | `docker compose exec minecraft rcon-cli` |
| One-off command | `docker compose exec minecraft rcon-cli say hello` |
| Restart | `docker compose restart minecraft` |
| Stop cleanly | `docker compose stop minecraft` (server saves on SIGTERM) |

## Changing mods

Edit `minecraft/pack.yaml`, rebuild, recreate:

```bash
cd minecraft && ./build.py && cd ..
docker compose up -d --force-recreate minecraft
```

Players update by re-importing the same `.mrpack` into their launcher.
See `minecraft/README.md`.

## Pre-generating chunks

Chunky is installed server-side. It generates terrain ahead of players
rather than during play, which matters here for two reasons: Terralith
and Tectonic make chunk generation much more expensive than vanilla, and
Distant Horizons builds its LOD data from chunks that already exist --
so an ungenerated world shows players an empty horizon regardless of
their render distance.

Run it from the console:

```bash
docker compose exec minecraft rcon-cli chunky radius 3000
docker compose exec minecraft rcon-cli chunky start
docker compose exec minecraft rcon-cli chunky progress
```

`radius` is in blocks from spawn. 3000 is a reasonable start for a small
group; 10000 is a lot of disk and hours of CPU.

Useful commands:

| Command | Effect |
|---|---|
| `chunky pause` / `chunky continue` | Suspend and resume; state survives restarts |
| `chunky quiet 30` | Progress updates every 30s instead of spamming |
| `chunky world the_nether` | Switch target dimension before starting |
| `chunky cancel` | Stop and discard the task |

**Do it with nobody playing.** Pre-generation saturates the CPU, and on
a 2-vCPU t3.large that means noticeable tick lag for anyone online.
Pause it before people join.

Watch disk while it runs -- the root volume is 25 GB and generated
chunks are the fastest way to fill it:

```bash
docker compose exec minecraft du -sh /data/world
df -h /
```

## Backups

The world is a directory: `data/world`. Stop the server (or run
`rcon-cli save-off && rcon-cli save-all` first) and tar it.

```bash
docker compose exec minecraft rcon-cli save-off
docker compose exec minecraft rcon-cli save-all
tar czf "backup-$(date +%F).tar.gz" data/world
docker compose exec minecraft rcon-cli save-on
```

`save-off` is what makes the snapshot consistent -- without it you can
tar a half-written region file. Nothing here schedules this yet; wire it
to cron or a systemd timer when you want it automatic.

## Whitelist

Set `MC_WHITELIST` in `.env`. It is applied on every start, which means
in-game `/whitelist add` does not persist across restarts -- edit `.env`
and restart instead. Set `MC_ENABLE_WHITELIST=false` to run open.
